# Ahmad Nouh — portfolio & AI Twin

[Live portfolio](https://me.nouhlab.com/) · [GitHub](https://github.com/ahmadnouh97)

A portfolio built with Vite, TypeScript, CSS, and Cloudflare Pages Functions. The AI Twin uses Groq GPT-OSS models with Cloudflare Workers AI fallbacks; explicit contact submissions send an email through Resend. Turnstile protects both routes.

## Run locally

Use Node.js **24** and npm.

```sh
npm ci
npm run build
npm run check
npm run preview
```

The complete Pages preview runs at http://127.0.0.1:8788. `npm run dev` runs only the Vite frontend at port 5173. HTML is generated by `scripts/render.ts` before each build.

## Automatic deployment

The [Deploy portfolio workflow](.github/workflows/deploy.yml) runs on every **push to `main`**, including merged pull requests. It installs locked dependencies, builds the static site, runs the existing checks, and deploys `dist/` plus the Pages Functions to `ahmad-nouh-portfolio`. Production remains at **https://me.nouhlab.com**.

Other branches do not deploy. Manual deployment is available under **Actions → Deploy portfolio → Run workflow**. Production runs are serialized to avoid overlapping deployments.

GitHub Actions configuration:

| Setting | Type | Value |
| --- | --- | --- |
| `CLOUDFLARE_ACCOUNT_ID` | Repository variable | Account containing the Pages project |
| `CLOUDFLARE_API_TOKEN` | Encrypted repository secret | Token restricted to that account, with **Account → Cloudflare Pages → Edit** |

The Groq, Resend, and Turnstile secrets remain in Cloudflare. They are not required in GitHub Actions or in the frontend build. A failed build or check prevents deployment.

This uses GitHub-hosted Linux runners and the existing Cloudflare Pages project; free-plan limits still apply. See [Cloudflare's continuous deployment guide](https://developers.cloudflare.com/pages/how-to/use-direct-upload-with-continuous-integration/).

## Source

- `src/content.ts`: public facts curated from the October 2, 2026 resume knowledge base, shared by the static pages and Twin. The private master document stays outside this repository.
- `scripts/render.ts`: homepage, four case studies, and privacy page.
- `src/style.css`: mineral/teal themes, inline experience, attributed results, contextual toolkit, responsive layouts, and native CSS motion.
- `src/main.ts`: saved theme/motion preferences, animated native chat dialog, streamed responses, stop/retry states, and contact form.
- `src/stream.ts`: shared SSE decoder; handles fragmented UTF-8 and CRLF.
- `src/chat-limits.ts`: shared answer/history limits and complete-turn pruning, including UTF-8 request size.
- `src/chat-retry.ts`: shared retry-header validation and visitor wait messages.
- `src/chat-format.ts`: safe text formatting for the Twin's headings and bullets; no generated HTML is executed.
- `src/chat-knowledge.ts`: shared public evidence, draft/review schemas, and server-controlled source links.
- `functions/api/`: public configuration, chat relay, lead notification, validation, and Turnstile verification.
- `public/ahmad-nouh-public-cv.pdf`: reviewed public CV without a phone number.
- `checks/site.test.ts`: Node's built-in checks for content boundaries, SSE, request validation, provider errors, and lead behavior.

The initial theme follows the device. The sun/moon switch saves a manual choice; the footer restores device theme. Motion starts enabled unless the device requests reduced motion. Visitors can explicitly enable it or pause it for the current visit; a saved pause does not disable future visits.

The Twin uses only production GPT-OSS models: Groq `openai/gpt-oss-120b`, Groq `openai/gpt-oss-20b`, Cloudflare `@cf/openai/gpt-oss-20b`, then Cloudflare `@cf/openai/gpt-oss-120b`, for retrieval, writing, and review. Cloudflare uses the Pages `AI` binding configured in `wrangler.toml`, with its native JSON-schema shape and raw response status. The 20B Cloudflare model goes first to conserve the independent free neuron allowance. Each stage moves to the fallback only on HTTP 429, tries each model once per round, and shares the existing inference deadline. Authentication/configuration errors and cancellations stop the chain. Preview models are excluded; Groq currently restricts the listed Llama production models to enterprise accounts. It first retrieves up to six relevant evidence IDs from a compact catalog. The schema enforces the six-ID limit; the server validates every returned ID, deduplicates valid selections, and keeps the first six ranked passages if a provider returns extra valid selections. Writer citations still reject more than six IDs. It then generates a reply using the complete retrieved excerpts and global factual boundaries from `src/chat-knowledge.ts`, derived from the same content as the pages. Uncached suggested recruiter questions and friendly messages use the same generation/review flow; all messages use semantic model evidence selection, with no greeting regex or fixed wording list. Pure social messages select no career evidence, while greetings mixed with professional questions select the relevant evidence. Prompts ask for one or two sentences for simple facts, natural brief acknowledgments, and proportionate detail for broader questions, in the visitor’s language. There is no automatic self-introduction or canned career response. Answer writing uses JSON object mode to avoid observed strict-schema clipping of free-form text; the server validates the exact shape, limits, and evidence IDs. Retrieval and review request JSON schemas; Groq supports strict schema mode, while Cloudflare uses native JSON mode. Both providers receive the same schemas and undergo the same server-side validation. A separate review call using the review model chain checks the draft against those full excerpts, global boundaries, and conversation for factual support, scope, relevance, and missing qualifications. Server guards also catch observed metric/split misinterpretations, unsupported employer tool claims, and dangling answer endings before review. Mixed employer sentences citing the documented Blink or Second Memory agent evidence go through contextual factual review rather than being rejected merely for mentioning MENT and LangGraph together. Review reports specific issues. A single correction attempt is shared between malformed/incomplete writer output, invalid evidence citations, Groq JSON-generation failures, and factual-review rejection. Corrected drafts still pass validation and factual review before delivery. Malformed review output gets one recovery call on the same draft at low reasoning effort, within the shared deadline; a valid negative review still requires writer correction. Malformed retrieval output, an exhausted review recovery, or an exhausted writer correction returns a specific error before any text reaches the visitor. Sanitized diagnostic logs contain a request ID, stage, model, provider status, error category, attempt, and elapsed time; they omit conversations, model answers, provider error bodies, and credentials. Timeouts and cancellations receive specific responses. Model review reduces unsupported claims but cannot guarantee factual correctness. Both JSON and SSE publish only the completed reviewed answer. Longer answers receive up to three server-controlled evidence links; short replies receive no automatic link block. Retrieval allows 300 completion tokens and generation 1,800. The primary review uses medium reasoning with 2,400 tokens; the 20B fallback first uses low reasoning with 1,200 tokens. Malformed or incomplete reviews get one low-effort recovery with 2,400 tokens (limits include hidden reasoning), with a shared 45-second inference deadline and an 8,000-character answer limit. Private-detail requests caught by the local guard return a direct-contact reply without inference. Stop cancels inference; only completed reviewed answers enter history. History retains complete recent turns within character and UTF-8 request limits and stays in page memory; no server transcript storage.

## Free inference capacity

Groq's free GPT-OSS limits are shared across the organization, so local diagnostic requests also consume production capacity. A normal reply needs three inference calls (selection, writing, and review), with bounded recovery calls when necessary. Additional API keys in the same organization do not create independent quota. Check the account's actual limits; see [Groq rate limits](https://console.groq.com/docs/rate-limits).

Selection uses evidence IDs, topic labels, tool names, and delivery/evaluation scope instead of passage previews. In live career-question checks, this reduced prompt tokens from 3,166 to 1,491 (about 53%) while retaining the relevant career evidence. Named-tool lookup was also checked against employer-specific passages. Generation and factual review still receive complete excerpts. The low-effort 20B reviewer also reserves less quota for its initial decision, with a larger recovery budget when needed. Live checks confirmed it accepted a documented pipeline outcome and rejected unsupported metric, dataset-split, and employer-tool claims. These changes reduce quota pressure; they cannot remove free-plan limits.

When all configured production models return 429, the API forwards the earliest valid `Retry-After` hint and names the wait in its error message. If no usable hint is available, it keeps a generic try-later message. The browser preserves the question, temporarily disables sending for a known wait, and allows manual retry afterward. Enter and New conversation do not bypass that page's wait. No browser inference retry runs during cooldown. If every configured model rate-limits a completed draft’s review, the server can wait once for a provider hint plus a one-second rounding margin, totaling at most 30 seconds and retry the review chain, only when at least eight seconds remain afterward in the original 45-second inference deadline. It preserves the draft, cancels on Stop, and returns 429 if the bounded retry is still limited. Selection and writing do not wait. A retry hint is an estimate; other visitors share the same quota.

For an independent free provider, [Cloudflare Workers AI](https://developers.cloudflare.com/workers-ai/platform/pricing/) offers 10,000 neurons per day on Workers Free, with requests stopping at the limit. Its [GPT-OSS-120B model](https://developers.cloudflare.com/workers-ai/models/gpt-oss-120b/) is intended for production. The account owner confirmed Workers Free. The `AI` binding enables this independent fallback when the PR is deployed, without adding an API key to the browser or signing up for a paid plan. The visitor disclosure names both inference providers. Keep the account on Workers Free to preserve the spending cap. Workers Paid can charge for excess usage. Cerebras currently provides a time-limited trial rather than a recurring free tier; Gemini's free tier also has distinct data-use terms. Provider offerings should be rechecked before integration.

Verified answers to the four public suggested questions are cached for ten minutes through Cloudflare’s Cache API, only for requests without history. Turnstile and origin validation still run before a cache lookup. Keys hash the public question, complete evidence, prompts, model chain, and a validation version; edits to facts or prompts automatically invalidate old entries. Increment `cacheVersion` in `functions/api/chat.ts` when validation or delivery rules change. Cache writes happen only after successful review. Errors, arbitrary visitor questions, and history-dependent answers are never cached. Cached responses retain the same JSON/SSE delivery format and are not cached in the browser. Cache failures fall back to inference. Cache entries are local to a Cloudflare data center and can be evicted early, so this is a quota-saving optimization rather than guaranteed availability. See [Cloudflare Cache API](https://developers.cloudflare.com/workers/runtime-apis/cache/).

## Service secrets

Copy `.dev.vars.example` to `.dev.vars` and supply:

- `GROQ_API_KEY`
- `RESEND_API_KEY`
- `TURNSTILE_SITE_KEY`
- `TURNSTILE_SECRET_KEY`

The file is ignored. Never prefix a secret with `VITE_`.

Production `SITE_ORIGIN` and `LEAD_FROM` are configured in `wrangler.toml`. Resend's sending domain must be verified; Turnstile must allow the exact production hostname. Both APIs check the request hostname, Origin, Turnstile hostname/action, and input limits. Emails are sent only after explicit form submission, to a fixed recipient with the visitor's address as reply-to.

For local form testing, use `http://localhost:8788` and set `.dev.vars` `SITE_ORIGIN` to that exact origin. Use Cloudflare’s documented dummy site key `1x00000000000000000000AA` and secret `1x0000000000000000000000000000000AA`. Dummy verification is restricted to HTTP loopback previews and still requires a successful Siteverify response. Real keys retain hostname/action validation; dummy keys are rejected on production origins and by the secret-upload helper. See [Cloudflare testing](https://developers.cloudflare.com/turnstile/troubleshooting/testing/).

To update production service bindings after a local Wrangler sign-in:

```sh
node scripts/sync-secrets.mjs
npm run deploy
```

The helper sends only the four service bindings through stdin. It does not print their values.
